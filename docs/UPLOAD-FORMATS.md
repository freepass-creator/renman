
## 2. CMS 자동이체 — 수입 채널

**표본**: `CMS.xlsx`

```
NO. | 회원번호 | 계약번호 | 회원명 | 청구월 | 납부자 휴대전화 | 상품 | 청구금액 | 수납상태 | 결제방식 | 결제수단 | 약정일 | 결제일(납부기간)
```

| 열 | 값 예시 | 쓰임 |
|---|---|---|
| 회원번호 | `00000305` | **계약 매칭 키**(8자리 0패딩 — 숫자로 읽으면 앞 0이 날아간다) |
| 계약번호 | `001` | 회원번호 하위. **회원번호+계약번호**가 진짜 키 |
| 회원명 | `97러0815 쏘노엠(남애진)` | **차량번호 + 상품 + 계약자가 한 칸에 뭉쳐 있다** |
| 청구월 | `2026/06` | 슬래시 구분 |
| 청구금액 | `720000` | |
| 수납상태 | `완납` | |
| 결제수단 | `CMS` | ← **채널 식별** |
| 결제일 | `2026-06-05` | 하이픈 구분(다른 파일과 형식이 다름) |

**핵심**: 이 파일에 `cmsId` 같은 단일 식별자가 **없다.** 은행 거래내역에는 `CMS집금`으로 **총액 한 줄**만 들어온다.
→ 매칭은 「CMS 총액 1줄 ↔ 이 파일 N줄」의 **1:N 대사(對査)**다. §6-4 채널 해석기는 이 구조로 설계해야 한다.

**회원명 파싱**: `97러0815 쏘노엠(남애진)` = 차량번호 + 차종 + 계약자.
`154모57`처럼 **뒤에 오는 경우**도 있다(`아산휴먼(진효정) 154모57`) → 위치 고정 금지, 번호판 정규식으로 뽑을 것.

**🔴 설계 수정 필요**: 오늘 `CorporateCard.cardLast4`(끝 4자리)로 매칭하게 만들었는데,
**신한 파일은 끝 4자리를 안 준다**(`****-9`). 앞 4자리(`9410`) + 끝 1자리(`9`) 조합이 실제로 얻는 정보다.

카드사마다 마스킹 위치가 다르므로 **원문 그대로 저장하고 정규화 함수로 비교**하는 쪽이 안전하다.

## 5. 파서가 지켜야 할 것 (실파일에서 나온 규칙)

1. **헤더 행을 고정하지 말 것** — 위에 계좌 표시줄이 오는 파일이 있다. 「거래일시」가 있는 행을 찾는다.
2. **시트를 전부 읽을 것** — 연도별로 나뉜다. 첫 시트만 읽으면 데이터를 잃는다.
3. **중복 헤더를 허용할 것** — 「메모」가 2개인 파일이 있다.
4. **회원번호는 문자열로** — `00000305`. 숫자로 읽으면 앞 0이 날아가 매칭이 깨진다.
5. **날짜 형식이 3종** — `2026.05.29 04:33` · `2026/06` · `2026-06-05`. 한 파일 안에서도 섞인다.
6. **사람이 넣은 열은 덮지 말 것** — `계정과목`·`업체명`·`상세내용`·`비고`는 손으로 분류한 값이다.
7. **입금/출금은 2열** — 부호 하나로 오지 않는다. 0이 채워져 있어 «빈칸=없음»이 아니다.
