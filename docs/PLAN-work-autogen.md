## 2. 설계 결정 — 언제 «진짜 업무»가 되는가

이게 이 작업의 전부다. 나머지는 여기서 따라 나온다.

### A안 — 즉시 실체화 (감지되면 곧바로 `work_item` 저장)

화면 로드/배치에서 어젠다 항목마다 `save('work_item', …)`.

- ✅ 업무원장 하나만 보면 된다
- ❌ **좀비 업무**: 검사를 마쳐 조건이 사라져도 이미 만든 업무는 남는다. 누가 닫나
- ❌ **쓰기 폭주**: 보유 113대 × 3~4종 = 수백 건. 화면 열 때마다 upsert + 감사로그
- ❌ **기한이 바뀌면** 옛 기한의 업무가 유령으로 남는다(계약 연장·검사일 변경)
- ❌ 서버 스케줄러가 없어 «누가 실행하나»가 미해결 → 결국 클라 로드 시점 = 위 문제 전부

### B안 — 지연 실체화 (제안으로 떠 있다가 **손대는 순간** 저장) ★권고

어젠다를 `source:'agenda'` **가상행**으로 업무원장에 합성한다. 사람이 담당자를 잡거나
상태를 바꾸거나 메모를 달거나 스누즈하는 **그 순간** `work_item`으로 굳는다(`workId = sourceKey`).

- ✅ **좀비가 구조적으로 불가능** — 손 안 댄 건 계산값이라 조건이 사라지면 행도 사라진다
- ✅ **쓰기 0** — 사람이 실제로 맡은 것만 저장된다
- ✅ **dedup이 공짜** — `workId = sourceKey` → 문서ID가 같아 두 번 생기지 않는다(별도 dedup 코드 불필요)
- ✅ 기존 패턴과 동일 — 과태료·문서함이 이미 이 방식으로 원장에 들어온다
- ⚠️ 가상행도 목록·필터·정렬·엑셀에 섞이므로 `WorkLedgerRow` 규약을 정확히 지켜야 한다
- ⚠️ 「자동배정」(규칙이 담당자를 정함)은 쓰기라서 Phase 2 — 규칙이 담당자를 정하면 그게 «손댐»이므로 같은 경로로 실체화된다

### C안 — 수동 승격 버튼만 (`[업무로]`)

- ✅ 제일 안전 ❌ 「데이터가 직원을 부린다」가 안 된다. 여전히 사람이 먼저 봐야 한다

### → **B안으로 간다.**

A의 이점(담당자·기한·상태전이가 붙는다)은 손대는 순간 실체화되므로 그대로 얻는다.
A의 세 가지 부작용(좀비·쓰기폭주·기한변경 유령)은 셋 다 안 생긴다.

## 3. `sourceKey` 규칙 — 근거키가 곧 문서ID

> 사장님 지시: 「매번 새로 만들면 중복이 쌓인다 → 근거키(`sourceKey` = 대상+종류+기한)로 dedup 필수」

```
sourceKey = auto:{kind}:{targetKey}:{dueDate}
             │      │        │          └ 회차 구분 — 검사·보험·세금은 매년 새 건이다
             │      │        └ 차량번호(정규화) 또는 계약키
             │      └ 어젠다 종류 5종
             └ 자동 생성물 표식(손으로 만든 업무와 섞이지 않게)
```

`work_item.workId = sourceKey` → 문서ID `{companyId}__auto:검사만기:12가3456:2026-09-01`.
**같은 근거로 두 번 저장해도 같은 문서다.** dedup 로직을 따로 쓰지 않는다.

### 기한이 바뀌면 (⚠ 이 설계의 유일한 함정)

계약을 연장하면 `dueDate`가 바뀌고 → `sourceKey`가 바뀌고 → 옛 키로 실체화된 업무가 남는다.

**규칙:** 같은 `(kind, targetKey)`의 **미완료 자동업무**가 있는데 어젠다의 `dueDate`가 다르면,
그 업무를 **새 키로 옮기지 않고 `dueDate`만 갱신**한다(rekey 아님 — 문서ID는 최초 것 유지,
`sourceKey`/`dueDate` 필드만 patch). 완료된 자동업무는 건드리지 않는다 → 다음 회차는 새 문서.

이 판정은 순수함수 `reconcileDirectives()`가 하고, **갱신은 사람이 그 행을 볼 때**만 일어난다
(자동 백그라운드 쓰기 없음 — B안 원칙 유지). 갱신 전까지는 행에 「기한 변경됨」 배지.

### 근거가 사라지면

실체화된 자동업무인데 이번 어젠다에 대응 항목이 없다 = 조건 해소(검사 완료 등).
→ **자동 종결하지 않는다**(감사 흔적이 사라진다). 행에 「근거소멸」 배지 + 일괄 [종결] 버튼.

| 어젠다 kind | 대분류 | 세부(`WORK_CATEGORIES`) | 대상 필수값 | 비고 |
|---|---|---|---|---|
| 검사만기 | 자산 | `검사` | plate | 그대로 있음 |
| 보험만기 | 자산 | `보험` | plate | 그대로 있음 |
| 세금 만기 | 자금 | `자금` | amount ⚠ | 자동차세 — 금액을 어젠다가 모른다(§7 가정 2) |

**세부 `반납·정산` 신설이 필요하다.** 계약 축의 활성 세부는 지금 `고객상담` 하나뿐이라
반납 만기를 담을 칸이 없다. 사장님이 계약 축 실행업무 후보로 이미 열거한 이름
(`인도`·`반납·정산`·`중도해지`·`연장·재계약`·`계약변경`) 중 하나를 그대로 쓴다.

⚠ **미결 판단(사장님)**: 「업무 = 예정·준비, 실제 전이는 계약화면」인가, 「업무에서 바로 실행」인가.
→ **가정 1(§7)**: 전자로 간다. 자동업무는 «반납 예정 — 회수 준비»를 뜻하고, 실제 반납 처리
버튼은 계약화면에 그대로 둔다(경로 이중화 방지). 업무 상세에서 계약으로 딥링크만 건다.

## 7. 가정 (사장님 확인 대상 — 틀리면 여기만 바꾸면 된다)

1. ~~가정~~ **✅ 사장님 확정 2026-08-07**: 반납·만기 자동업무 = **예정·준비**까지.
   실제 반납 전이는 계약화면 버튼 하나만 유지. 계약 축 나머지 세부(인도·중도해지·연장·계약변경)도 같은 규격.
2. **세금 만기 금액**: 어젠다에 자동차세 금액이 없다. 자금 축 필수값 `amount`를
   가상행에서는 **강제하지 않고**(0), 실체화 시 사람이 채우게 한다.
   → 대안: `vehicle.vehicleTaxAmount` 필드가 있으면 그걸 쓴다(구현 중 확인).
3. **스누즈 = 실체화**. 「나중에 볼래」도 사람의 결정이므로 `work_item`으로 남긴다
   (`status:'보류'` + `snoozeUntil`). 별도 오버레이 엔티티를 만들지 않는다.
4. **담당자 자동배정은 이번 범위 밖**(Phase 2). 규칙(회사별·종류별 기본담당자)이 없다.
5. 자동업무의 `priority`는 어젠다 status에서 파생 — 어김=`긴급` · 임박=`높음` · 예정=`보통`.

**실제 결과: 22건 통과.** 위 10개 + 구현 중 드러난 것들:
- **과태료는 제안하지 않는다** — `penalty` 가 이미 원장 원천이라 자동 제안까지 만들면 같은 고지서가 두 줄이 된다(`DIRECTIVE_KINDS` 에서 제외).
- **`workGroup(세부) === 세부`** 회귀 테스트 — 신규 세부 `반납·정산` 이 정규식에 안 걸려 조용히 「기타」로 떨어졌다.
  `workGroup` 앞에 «정규 세부값이면 추측하지 않는다» 를 넣어 고침. 세부가 늘 때마다 같은 사고가 나는 자리였다.
- **보류(스누즈)는 종결이 아니다** — 미룬 일도 기한 변경은 따라간다.
- **금액을 모르는 근거는 `amount` 를 만들어내지 않는다**(0원과 «모름»은 다르다).
